# Reviews
## Reviewer 1
1. The main claim of the paper is that Hyperiax makes BFFG practical for substantially larger trees and landmark datasets. The two examples show that analyses of this size can be run, but I could not find runtime information or details of the hardware used. At present this demonstrates feasibility more clearly than computational scaling. Could the authors report approximate wall-clock times and the hardware used for the two analyses? A small comparison showing how runtime changes with tree size and/or landmark number would also be useful if this can be included without substantially expanding the paper. I do not think an extensive benchmarking exercise is necessary, but some quantitative measure of the computational improvement seems important given that this is the principal advance of Hyperiax.
2. Related to the above, the butterfly and beak datasets contain similar numbers of landmarks, although the beak data are three-dimensional. I wonder whether an example with a substantially larger number of landmarks would provide a useful additional demonstration of the claimed scaling with shape resolution. OR, if you do not think an additional biological case study is necessarily required, it may be more informative simply to show how computational cost changes as the number of landmarks increases, perhaps by subsampling one of the existing datasets at several landmark resolutions. This seems particularly relevant because one of the main claims of the paper concerns scaling with shape resolution.
3. I wasn't clear from the manuscript how branch lengths are treated in the two empirical analyses. As the stochastic process describes morphological change through time along the phylogeny, this seems relevant to the interpretation of k alpha as an evolutionary-rate parameter to me. Could the authors briefly state whether the published branch lengths are used directly or rescaled before analysis, and clarify that inference is conditional on a single fixed phylogeny? I do not think phylogenetic uncertainty needs to be incorporated for these demonstrations, but the treatment of the phylogeny should be explicit.
4. Table 1 reports R hat for the model parameters, which is useful, but Fig. 1 also relies on posterior sampling of a high-dimensional ancestral root shape. Could the authors provide a similarly compact convergence diagnostic for the root, or a summary across the latent ancestral coordinates, perhaps in the reproduction repository if space is tight? I would also find ESS useful here. I do not think every ancestral coordinate needs to be tabulated, but some indication that this component of the chain is mixing adequately would make the reconstruction easier to assess.
## Reviewer 2
1. Hyperiax seems to provide nearly full control of model specification through python. I also noticed that the hyperiax-phylo repository contains YAML configuration files (e.g., beak.yaml) that allow analyses to be configured relatively quickly. I think this functionality is particularly useful from a practical standpoint, and worth mentioning explicitly in the main text.
2. Also, I would recommend providing a short tutorial in hyperiax github pages demonstrating how to set up and run an analysis using a YAML configuration file. Many users in the phylogenetics community may find direct specification of complex models in python challenging, whereas a simple YAML-based workflow could make Hyperiax substantially more accessible. Highlighting this option can therefore increase the number of users for this software.
